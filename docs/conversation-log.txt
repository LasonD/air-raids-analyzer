  Text data: what we covered

  Covered:
  - Sources: two public Telegram channels since 1 Jan 2026:
    - the official Air Force channel, @kpszsu;
    - the volunteer alert-map channel, @povitryanatrivogaaa.
  - Parsing: about 78,000 posts become events: time, region, and threat kind
    (drone, missile, aviation, explosion, all clear).
  - Use in the model: they are features (for example, a post naming the region
    in the last hour), counting only posts published before the forecast time.
  - Measured effect: Telegram helps for the first 1–3 hours, adding +1.1 points
    (95% range +0.3 to +1.8) at quiet moments. After that it adds nothing, so
    the main model stops using it beyond 3 hours. That choice was made on the
    validation weeks, not the test weeks.
  - Live: the app reads the newest posts straight from Telegram.

  Not covered. Ordered by what I think would help most:
  1. The alert channel @UkraineAlarmSignal: it posts alerts live, per district.
     This is the main gap. Today, live posts can't enter a forecast until the
     daily alert file catches up. It's already named as the next step in the
     README.
  2. The Air Force's morning summaries ("overnight the enemy launched N drones,
     M missiles"): the parser drops them as summaries. Their counts could give a
     daily "intensity" signal for the 4–24 h range, where we currently only
     match the usual daily rhythm.
  3. Media: the alert-map channel's route maps are images, and we skip them
     (most are edited posts anyway). Reading them would need image recognition,

  No leakage: how it's enforced

  The README has a section on this ("No data leakage: how it is enforced"):
  1. Training rows: each week's model trains only on rows whose 24 target hours
     all ended before that week. backtest.py asserts this.
  2. Inputs:
     - One function builds the features, and it only sees hours before the
       forecast time, alerts that started before it, and posts published before
       it.
     - An alert still running at that time is treated as having no known end.
  3. Tested:
     - tests/test_leakage.py rebuilds every feature from data cut off at the
       forecast time and requires identical values. It also plants a feature
       that peeks at the outcome and checks that the test catches it.
     - On its first run it caught a real bug: countrywide counts depended on
       which duplicate copy of a post was kept.
     - tests/test_replay.py checks that the app's replay clock reproduces the
       committed results and that no outcome after "now" is known.
  4. Telegram edits:
     - Telegram shows the original publish time but the latest text. The
       alert-map channel updates route summaries in place, so an edited post
       could carry later information. Edited posts are excluded, and text after
       "UPD" is cut.
     - We found this ourselves: excluding them removed most of that channel's
       apparent advantage.
  5. Model choices: they were made on 4 validation weeks. The last 4 test weeks
     were scored once. Picking the best source set on the test chart would
     itself have been leakage.
  6. The data snapshot: the alert file leaves out alerts still running when it
     was made, so the data counts as complete only up to 00:00 UTC.

  What's left, and already listed in the README's limitations:
  - Short alerts: alerts with no all-clear get a 30-minute end in the source,
    which is hindsight a real-time observer wouldn't have had.
  - Archive corrections: we use today's version of the alert history, so any
    later corrections to the archive are invisible.
  - Parser rules: town names and parser rules were written while looking at

● It's 22:49 Kyiv, 26 minutes before the 23:15 code stop, so I'll keep this
  short.

  1. Why Parsing shows two sources. Parsing only applies to text, and only the
  two Telegram channels are text.
  - The alert history is already a table (region, start, end). It goes straight
    to Format.
  - The fourth source, the official alert file (@air_alert_ua), stops on 7 Sep.
    It's used only to measure how often the two alert records disagree (about
    19% of oblast-hours), never as model input.
  - The chart in your screenshot is missing the alert-map bars because its
    legend entry was clicked. Plotly hides a series when you click its legend
    entry. That should be off on read-only charts, and it's a one-line fix.

  2. Patterns per oblast. The model already works per oblast: each region has
  its own history, neighbours and usual daily rhythm.
  - The "After an alert" chart is computed within each oblast and then averaged,
    so differences between oblasts don't pass for persistence.
  - The "Region and hour" heatmap is per oblast.
  - The rest are countrywide. A "Region: all / one oblast" filter for those
    charts makes sense, about 15–20 minutes.

  3. Map colours. They're correct in principle but hard to read.
  - What it uses:
    - one blue hue, where a stronger colour means a higher chance (lighter in
      dark mode, darker in light mode);
    - grey for Crimea and Luhansk (no usable alert data, so not forecast);
    - red reserved for real alerts (the red outline in hindsight).

    This is colour-blind safe.
  - The problem is reading it:
    - 30% and 45% look almost the same;
    - in dark mode the low end blends into the background and the grey regions;
    - nothing on the map says what the grey means.
  - Fix: five stepped bands (under 10%, 10–25%, 25–50%, 50–75%, over 75%) and a
    "grey = not forecast" note. A warm "heat" palette would read more naturally
    as risk, but it would clash with the red outlines for real alerts. About 10
    minutes.

  4. How Forecast works. At "now", the model trained on data before this week
  gives each of 24 regions a chance of being under alert in each of the next 24
  hours.
  - Map: one of those hours, chosen with "Hours ahead".
  - "Colour by": swaps in the usual daily rhythm for comparison.
  - "What happened": outlines in red the regions that really had an alert. This
    only works for past moments.
  - Right side: this week's results so far, plus one region's 24 hours as
    forecast, rhythm and real alerts.

  Is it clean and intuitive? Honestly, no.
  - There are five controls in one row.
  - You see one hour at a time, so "where and when in the next 24 h" never shows
    at a glance.
  - "Success" is an abstract "% better than rhythm".

  A better design:
  - Top line: for example, "Next 24 h: most likely Kharkiv, Sumy… · expected 7.5
    regions next hour".
  - Main view: a grid of 24 regions × 24 hours, so all 576 forecasts are visible
    at once.
  - Past moments: real alerts marked on the grid, and one plain line such as
    "caught 41 of 52 alert-hours; usual rhythm: 33".
  - Tabs: the map and the single-region view become secondary.
